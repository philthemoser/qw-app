01 — Start here

What it is

Tinuë plays a full backing band — pad, piano, bass, and three percussion voices — from chord progressions the user arranges into sections. They build a song, hit play, and the app performs it like a band following the chart.

One idea runs through everything: opinionated and fast. The app makes the musical choices so the user doesn't have to fiddle. That's why there's no sound browser, no deep mixer, no note editing. Its value is in what it leaves out. When you add things, keep that in mind — the easy move is always to pile on options, and that's usually the wrong one.

No backend, no database, no accounts. It's a single web page plus audio files, hosted for free on GitHub Pages. That simplicity is a feature — there's very little that can go wrong operationally.

02 — The setup

How it's built

Everything lives in one GitHub repo: github.com/philthemoser/qw-app. Here's what's in it:

In the repoWhat it is
index.htmlThe whole app, in one file. This is what actually runs in the browser.
samples/All the audio — piano, pad loops, percussion. Organised in folders.
manifest.webmanifestThe "Add to Home Screen" name and settings.
icons/The app icon in a few sizes.

There's also the source file, chord-groove-v21.jsx. This is the human-friendly version of the code — it's where all the real work happens. Think of it as the editable original; index.html is the packaged-up copy that browsers can run.

The one thing to internalise

You edit the .jsx file, then "build" it into index.html. Never edit index.html by hand — your next build wipes it out. If you're vibe coding, tell your AI: "the source is chord-groove-v21.jsx; index.html is generated from it."

What "building" means

The .jsx file uses modern React syntax browsers can't run directly, so a tool called Babel translates it into plain code and wraps it in the index.html shell. It's a small, mechanical step — translate, wrap, done. When you work with an AI assistant, it handles this for you; just ask it to "compile the jsx to index.html" when you're ready to ship.

If that manual step ever annoys you, the cleanest upgrade is to switch the project to Vite (a standard build tool) — it does the translating automatically every time you save. See What's next.

03 — Workflow

How to change it

The loop for any change is the same four steps:

1 · Edit

Change the .jsx source — yourself or by asking an AI.

2 · Build

Compile the .jsx into index.html.

3 · Check

Open the HTML and make sure it loads and plays.

4 · Ship

Commit index.html to the repo; the live site updates itself.

The check in step 3 matters

This app has one failure mode worth knowing: if the code has a certain kind of mistake, the whole screen goes blank beige instead of showing an error. So always open the built file and confirm it actually appears before you ship. If it's blank, the last change broke something — undo it and try again, or ask the AI to look at the browser console for the error.

Vibe-coding this app well

It responds well to describe-what-you-want coding, with two habits that save pain:

  • Give the AI the whole .jsx file as context, and tell it to return the edited file or a specific edit. It's one file, so there's no hunting across a codebase.
  • Change one thing at a time and check it. Because a bad change blanks the screen, small steps make it obvious which change caused a problem. Big multi-feature rewrites are where this app bites.

04 — The map

The parts, in plain terms

You don't need to understand the internals to work on it, but knowing what the main pieces are helps you describe changes clearly. Here's the whole app in six boxes.

One genuinely clever bit worth knowing

Each section has a single Intensity slider. Behind it, the app auto-generates the whole groove — how busy the drums are, how open the filters sit — from that one number. That's why a section can go from sparse to full with one control. If you ever want to change how "busy" feels at a given intensity, that's the applyIntensity logic.

The song, concretely

If you want to generate songs (say, to pre-load a chart library), this is the shape to produce. A real example is on disk as exported JSON — point your AI at one and ask it to match the format.

{
  title, key, scale, bpm, timeSig,     // "Holy Forever", "C", "major", 70, "4/4"
  sections: [
    {
      name, repeats,                   // "Chorus", 2
      chords: [ { label, root, beats, … } ],   // each chord carries its own info
      dyn: { intensity, …groove… }     // the section's feel
    }
  ],
  mix, instruments                     // fader levels & which voices are on
}

05 — Look before you leap

Where to be careful

Most of the app is safe to change freely. A few areas are delicate — not off-limits, just worth a careful look (and a careful prompt to your AI) rather than a blind rewrite.

The sound engine and the player

The code that builds the instruments and the clock that drives them is the subtle heart of the app. It works, but it's easy to break in ways that only show up while a song is playing — like a change you make mid-song not taking effect. If you're asking an AI to touch this, tell it to be surgical and explain what it's changing, rather than rewriting the whole engine.

Changing key while a song plays

There's a known rough edge: the piano uses two sets of samples (one anchored around C, one around G) and picks which to use when you press play. If the user changes key mid-song across the boundary between them, it can sound wrong. The real fix is loading both sets at once — it's on the roadmap. Just know this is a known issue, not something you broke.

Instrument levels

Each instrument has a built-in level adjustment so the mix sits balanced. If you swap a sample and it's suddenly too loud or quiet, there's a small number to tweak — but it appears in two places for each instrument, and both must match. If you change one, change both, or ask your AI to "update the trim in both the engine and the live mixer."

The iOS silent switch

On iPhones, flipping the physical silent switch mutes the app's sound, and there's no way around it from a web app — it's an Apple rule, not a bug. The accepted answer is: tell users to turn off silent mode. The only real fix would be turning this into a true native app (a bigger project).

The design scale

The styling uses a deliberately small set of sizes, spacings and colours — it was cleaned up specifically so everything feels consistent. When adding UI, reuse the existing values rather than inventing new ones. Your AI will do this if you tell it "stick to the existing design tokens / sizes."

06 — The fun stuff

Easy wins & safe swaps

These are the low-risk, high-reward changes — good places to start.

Swap or improve the samples no code

The app finds audio by filename. Re-record a sound, keep the exact same filename, drop it in the samples/ folder, and the app uses it — no code change at all. One catch: browsers cache audio aggressively, so after replacing a same-named file, check it in a private/incognito tab to be sure you're hearing the new version.

Change wording, colours, labels easy

Text, the welcome message, button labels, the colour palette — all straightforward edits in the source. Low risk; just rebuild and check.

Add chord progressions easy

The "Choose" menu offers ready-made progressions. Adding one is a small, self-contained edit to a list — a very safe first change to try.

A chart library page nice project

A browsable page of pre-made songs, each with a "Copy" button that puts the song onto the clipboard so the user can paste it into the app's Import. The app already exports songs in the right format — so this is a separate little page, not a change to the app itself. Low risk because it can't break the main app.

Alternate percussion sounds nice project

Give the three percussion slots a pool of sounds to choose from (hihat, snare, clap, rimshot, etc.). These are tiny one-shot files, so it's cheap. The trick is loading them all up front so switching is instant, and giving each a level adjustment so swapping doesn't jump in volume.

07 — Going live

Putting it live

Where

GitHub repo philthemoser/qw-app, hosted free on GitHub Pages.

How

Commit to the main branch. The site rebuilds itself automatically.

Address

philthemoser.github.io/qw-app

That's the whole deployment. Push your updated index.html (and any new samples) to main, wait a moment, refresh the live site.

Two harmless quirks

GitHub sometimes says "Deployment failed, try again later" and then works on the next push — usually nothing's actually wrong. And it occasionally warns that an old Node version is deprecated; that's a maintenance note, not a problem today.

Once it's live and people use it

Don't edit the live version directly to test ideas. Try risky changes on a copy first. GitHub keeps every old version, so if a bad change does go out, you can always roll back — but it's calmer not to need to.

About "offline": the app can be added to a home screen and shows the Tinuë name and icon, but it still needs internet to run — there's no offline caching yet. Making it work fully offline is a roadmap item.

08 — Next

What's next

Where the project was heading, roughly most-useful first:

  1. fix  Live key changes across the sample boundary — load both piano sample sets at once so changing key mid-song always sounds right.
  2. big  Work offline — make it keep working without internet once loaded (a "service worker" and caching the audio). First decide: is a web app enough, or does the silent-switch issue push toward a real native app?
  3. infra  Switch to Vite — removes the manual build step so editing is smoother. A good early investment if you'll work on this a lot.
  4. content  The chart library page — pre-made songs ready to copy in.
  5. feature  Alternate sounds — start with the percussion pool (cheap), then maybe an alternate bass tone. Keep each addition small so the app stays fast and focused.

Things that were deliberately left out

Dark mode (it's intentionally light for bright rooms/stages), lots more instruments, cloud sync and accounts, lyrics, and a full sound browser. These were all considered and declined on purpose — they'd make the app slower to use and blur what it's for. If you're tempted by one, that's worth a second thought first.

09 — Keep it sane

Rules of thumb

  • One change at a time, then check it loads. The blank-beige failure makes small steps worth it.
  • Edit the .jsx, build to index.html. Never hand-edit the built file.
  • Swapping samples is free and safe. Same filename, drop it in, check in a private tab.
  • Be gentle with the sound engine. Ask for surgical edits there, not rewrites.
  • Reuse the existing design values. Don't invent new sizes and colours.
  • Protect the feel: opinionated and fast. When in doubt, fewer options, not more.
Fastest way to get oriented

Open the live app, then open chord-groove-v21.jsx next to it. Press play in the app and skim the file top to bottom once — you don't need to understand every line, just get a feel for where the music theory, the instruments, and the screen layout each live. Then make one tiny change (a label or a colour), build, and ship it. Once you've done the full loop once, the rest is just more of that.
